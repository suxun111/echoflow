## 结论

截至 `0e3d140` 审计基线，本机 MOSS 不能通过“填写 `MOSS_BASE_URL`”直接接入 EchoFlow。两边不仅是路由不同，而是成功结果、幂等、恢复、安全和取消语义不同。

从第一性原理看，EchoFlow V1 的用户价值是“看到准确英文句子，并按时间边界逐句循环练习”，不是卡拉 OK 式逐词高亮。因此，**可靠的分段/Cue 级时间戳足以支撑 V1 主路径，逐词时间戳应当作为后续增强，而不应被伪造**。

确认决策：把 G3 的最小成功结果从“必须逐词时间戳”调整为“必须有完整英文分段、每段准确起止时间；逐词时间戳可选”。实现不得通过平均分配时长或字符数伪造单词边界。

## 契约差距

| 能力 | EchoFlow 当前冻结契约 | 本机 MOSS 当前实现 | 判断 |
|---|---|---|---|
| 提交输入 | JSON、短期签名音频 URL、稳定幂等键 | multipart 文件上传 | 不兼容 |
| 认证 | Bearer Token；回调 HMAC | 未发现 API 认证 | 不可暴露到公网 |
| 幂等 | 可按幂等键查询；响应丢失后复用同一任务 | 无幂等键与查询接口 | 重试可能重复计算 |
| 结果状态 | `succeeded/failed/cancelled` 等机器状态 | 转写后进入 `waiting_review` | 不能直接映射成功 |
| 结果结构 | `language=en` 与 `words[{text,startMs,endMs}]` | `segments[{id,start,end,speaker,text}]` | 只有分段级时间 |
| 取消 | 运行中可取消，迟到结果不得复活 | DELETE 仅适用于非运行任务 | 不满足取消语义 |
| 重试 | 相同稳定身份重开 | rerun 生成新 Job ID | 身份语义不同 |
| 恢复 | 数据库为事实源；服务重启后继续或可协调 | 进程内队列；重启时运行中任务被标记失败 | 不满足长任务恢复 |
| 回调 | 签名回调为主、轮询兜底 | 无回调 | 只能轮询且仍缺身份语义 |

因此，直接改 EchoFlow Adapter 去迎合现有 MOSS 也不能解决生产正确性；它只会把重复任务、崩溃恢复和取消泄漏藏到接口后面。

## 第一性原理判断

### 用户真正需要的最小事实

对口语影子学习，一条可练习 Cue 至少需要：

- 完整、可读的英文文本；
- 与视频同一时间轴上的准确 `startMs/endMs`；
- Cue 顺序单调、无越界、无明显缺失；
- 点击 Cue 能准确跳转并循环；
- 结果可恢复、可重试，且不能发布半成品。

逐词时间戳主要服务于逐词高亮、单词级点击、精细发音对齐和在一个长分段内重新切句。它不是 V1 已确认的逐句循环、录音回听和进度恢复的必要条件。

### 不能接受的捷径

不能把一个 MOSS 分段的时长平均分配给其中各单词，也不能仅按字符数生成单词边界。这种数据在格式上满足 `words[]`，但在事实层面是假的，会让后续逐句切分、跳转和验收产生系统性误差。

如果一个 MOSS 分段过长，V1 应保留真实分段边界，或把它送入独立的强制对齐阶段；不能在没有声学证据时制造子时间戳。

## 两条可选路线

### A. 分段时间戳作为 V1 最小契约（推荐）

调整 G3 合同，使 Provider 结果至少包含：

```text
language: "en"
segments: [{ text, startMs, endMs, speaker? }]
words?: [{ text, startMs, endMs }]
```

发布时一个真实 MOSS segment 默认映射为一个 Cue；只有存在真实单词/强制对齐证据时，才允许进一步切分。保留 `words` 为可选能力，未来可无破坏升级。

优点：与 MOSS 原生能力一致，最快形成真实字幕和逐句练习闭环；避免伪造精度。

代价：需要更新 PRD、G3 合同、共享契约、合并校验和相关测试；极长分段的练习体验需要后续优化。

### B. 保持逐词时间戳为硬门槛

在 MOSS 分段结果后增加声学强制对齐/第二 ASR 阶段，输出有证据的逐词时间戳，再进入现有 EchoFlow 合并和发布流程。

优点：保留当前冻结合同，支持更精细的字幕交互。

代价：新增模型、算力、失败状态、对象生命周期和长视频耗时；真实 MOSS 接入周期明显增加。

## 推荐接入架构

无论选择 A 还是 B，都建议在 MOSS 模型服务前增加一个薄的 Provider Gateway，而不是让 EchoFlow 依赖当前 GUI 服务的进程内行为：

```text
EchoFlow Worker
  -> 带认证的 Provider Gateway
     -> 持久化幂等键 / Job / Attempt
     -> 持久化队列与重启协调
     -> 拉取短期签名音频或受控 multipart 转发
     -> MOSS 推理服务
     -> 标准化 segment/word 结果
  -> EchoFlow 原子字幕发布
```

Gateway 的最低要求（第一版路由固定为 `/api/provider/v1`）：

1. Bearer 认证，且不向 MOSS 暴露对象存储永久凭据；
2. 稳定幂等键唯一约束及按键查询；
3. Job/Attempt 持久化，不以进程内 Map 或线程队列作为事实源；
4. 明确的 submit/query/result/cancel/retry 语义；
5. 重启后可恢复，或至少可安全协调已经被接受的任务；
6. 结果保留模型版本、输入校验和、分段时间与错误分类；
7. 真实取消或明确的不可取消状态，并确保迟到结果不能发布；
8. readiness 区分“HTTP 活着”和“模型/设备可推理”；
9. GPU/CPU 运行配置、模型缓存和容量指标可观测；
10. 回调可后置，但轮询必须先具备完整幂等和恢复语义。

## 建议执行顺序

1. 用户确认 A 或 B；这是产品范围和验收标准变化，不能由实现者代替决定。
2. 按选择更新 PRD、G3 合同和共享结果契约，先写迁移/兼容测试。
3. 为 MOSS 建立 Provider Gateway；保留现有 GUI 路由，不让 EchoFlow 绑定 GUI 语义。
4. 准备可复现的 GPU 或明确可接受的 CPU 运行环境，确认模型缓存、磁盘和运行依赖。
5. 先跑 30 秒真实英文样本，检查文本、时间边界、任务恢复和资源占用。
6. 再跑 5/30/60/120 分钟矩阵，以及取消、重启、响应丢失和失败恢复。
7. 独立 Reviewer 审核最终代码锚点；证据进入唯一 trunk 后才关闭 G3。
